# Topic: clob

# Polymarket CLOB V2 wire details for the M1 recorder (BTC 5m), checked 2026-10-26

**Sources and tags.** Live captures were taken from Serbia between 16:12 and 16:16 UTC. Nothing was blocked and no auth was used.
- Windows used: live `btc-updown-5m-1793031000` (cid `0x6fc2dbad…71eb7`), next `btc-updown-5m-1793031300` (cid `0xe3152b33…4383e`), and one that ended more than 10 minutes earlier, `btc-updown-5m-1793030400` (cid `0xa086ff5c…a8dec`).
- Source code checked: `Polymarket/rs-clob-client-v2@main` (last push 2026-10-19).
- Tags: [live-verified], [source-code], [docs], [unverified].

## 1. Market WebSocket

### Connection and subscribe

- **URL:** `wss://ws-subscriptions-clob.polymarket.com/ws/market`. No auth. [live-verified]
- **Initial subscribe** (what I sent; it worked) [live-verified]:
  ```json
  {"assets_ids":["<up_token>","<down_token>"],"type":"market","custom_feature_enabled":true}
  ```
  - The Rust SDK sends this form instead: `{"type":"market","operation":"subscribe","markets":[],"assets_ids":[...],"initial_dump":true}`, plus `"custom_feature_enabled":true` when you opt in. [source-code: src/clob/ws/types/request.rs]
  - `initial_dump` defaults to `true`. The 100-token cap per connection was removed on 2025-05-28. No other per-connection limit is documented. [docs: changelog]
- **Add assets on an open connection** [live-verified]:
  ```json
  {"assets_ids":["<new_up>","<new_down>"],"operation":"subscribe"}
  ```
  - The book snapshot for the new tokens (a JSON array of 2 `book` objects) arrived 51 ms after sending.
  - This frame has no `type` field and no `custom_feature_enabled`. Custom-feature events still arrived for the original assets.
- **Remove assets** [live-verified]:
  ```json
  {"assets_ids":[...],"operation":"unsubscribe"}
  ```
  - The last event for the removed tokens came before the unsubscribe was sent, and none came after it in the following 6.5 s. The server sends no acknowledgement frame.
- **Heartbeat:**
  - The client sends the text frame `PING` and the server replies with the text frame `PONG` (not JSON) in about 50 ms. [live-verified]
  - Docs say to send it every 10 s. [docs]
  - The SDK defaults to sending every 5 s and treats the connection as dead if no PONG arrives within 15 s. [source-code: src/ws/config.rs]
  - I didn't test how long the server waits before closing an idle connection. [unverified]
- **Reconnect:**
  - The SDK uses exponential backoff: 1 s initial, ×2, 60 s cap, retrying forever. [source-code]
  - Missed events are not replayed. After a reconnect, resubscribe; the `initial_dump` snapshot re-bases the book.

### Framing

These points are all [live-verified]:
- The initial snapshot (and the snapshot after a dynamic subscribe) is a **JSON array** of `book` objects, one per asset.
- Every other event is a **single JSON object per frame**.
- `PONG` is plain text.
- **Parser rule:** if the first byte is `[`, treat the frame as an array; if `{`, as an object; otherwise it's text.
- **Volume:** the live BTC 5m window produced about 380 frames/s (6,731 frames in 17.7 s). In 18 s that was 6,101 `price_change`, 326 `book`, 164 `last_trade_price` and 138 `best_bid_ask`. After the window ended, traffic fell to about 4 frames/s.
- **Timestamps** are strings of epoch milliseconds and are **not monotonic** across frames (I saw `…505` arrive after `…506`). Order events by arrival, not by timestamp.
- **There is no sequence number.** [live-verified, source-code, docs]

### Event types (real samples, trimmed)

All strings below are exactly as received. Numbers are strings throughout.

**`book` as an initial snapshot (array element)** [live-verified]
- It has extra fields `tick_size` and `last_trade_price`.
- **Bids are sorted ascending (best bid last); asks are sorted descending (best ask last).**

```json
{"market":"0x6fc2dbad…71eb7","asset_id":"2280068662…4404330","timestamp":"1793031216412","hash":"7a40a4e8befc0cc704da22748ccd645950628019","bids":[{"price":"0.01","size":"9346"},…,{"price":"0.05","size":"323.89"}],"asks":[{"price":"0.99","size":"9152.55"},…],"tick_size":"0.01","event_type":"book","last_trade_price":"0.050"}
```

**`book` mid-stream (standalone object)** [live-verified]
- It arrives as a pair (one per token) after trades or best-bid/ask changes, roughly 9 per second per token.
- It has **no** `tick_size` or `last_trade_price` fields.

```json
{"market":"0x6fc2…","asset_id":"2280…","bids":[...],"asks":[...],"hash":"…","timestamp":"1793031216426","event_type":"book"}
```

**`price_change`** [live-verified]
- On these binary markets it always carries 2 entries: the level on one token mirrored onto the other (BUY p on Up ↔ SELL 1−p on Down).
- `size` is the **new absolute size at that level**; `"0"` means the level is removed.
- Each entry's `hash` is the post-change book hash for that asset.

```json
{"market":"0x6fc2…","price_changes":[{"asset_id":"2280…","price":"0.02","size":"4126.32","side":"BUY","hash":"7a40a4e8…","best_bid":"0.05","best_ask":"0.06"},{"asset_id":"1274…","price":"0.98","size":"4126.32","side":"SELL","hash":"3e68515a…","best_bid":"0.94","best_ask":"0.95"}],"timestamp":"1793031216412","event_type":"price_change"}
```

**`last_trade_price`** [live-verified]

```json
{"market":"0x6fc2…","asset_id":"1274…","price":"0.95","size":"6.3263","fee_rate_bps":"0","side":"BUY","timestamp":"1793031216420","event_type":"last_trade_price","transaction_hash":"0x2fc0e9db…0fa9"}
```

**`best_bid_ask`** (needs `custom_feature_enabled`) [live-verified]

```json
{"market":"0x6fc2…","asset_id":"2280…","best_bid":"0.05","best_ask":"0.06","spread":"0.01","timestamp":"1793031216426","event_type":"best_bid_ask"}
```

**`tick_size_change`** [live-verified]
- It fired 31 s after the window ended, when the price reached about 0.999/0.001.
- **Each asset's event arrived twice** in the same batch, so deduplicate on (asset_id, timestamp, new_tick_size).

```json
{"market":"0x6fc2…","asset_id":"2280…","old_tick_size":"0.01","new_tick_size":"0.001","timestamp":"1793031331574","event_type":"tick_size_change"}
```

**`new_market`** (custom feature) [live-verified]
- It is **broadcast for all markets regardless of your `assets_ids`**: I received 9 Süper Lig markets. Filter it, or drop it before recording.
- Keys: `id, question, market, slug, description, assets_ids, outcomes, event_message{id,ticker,slug,title,description}, timestamp, event_type, tags, condition_id, active, clob_token_ids, sports_market_type, line, game_start_time, order_price_min_tick_size, group_item_title, taker_base_fee, fees_enabled, fee_schedule{exponent,rate,taker_only,rebate_rate}`. All numbers are strings except `active` and `fees_enabled`, which are booleans.

**`market_resolved`** (custom feature) — **not captured.**
- The window I watched hadn't resolved 61 s after its end, which is past both 19 s capture slots, and another 42 s later REST still showed it unresolved. The poller's first sample, 609 s after the end, already showed it resolved.
- Fields per docs and SDK: `id, market, assets_ids, winning_asset_id, winning_outcome, timestamp, event_type`, plus optional `question, slug, description, outcomes, event_message`. [docs, source-code]
- It is not known whether it is broadcast to every subscriber like `new_market`. [unverified]

### Gap detection

There are no sequence numbers, but the `hash` is reproducible, which gives a per-asset integrity check. [live-verified]
- **Hash formula:** `hash = sha1_hex(compact JSON of {"market","asset_id","timestamp","hash":"","bids","asks","min_order_size","tick_size","neg_risk","last_trade_price"})`.
  - Use exactly that key order, `separators=(',',':')`, the server's string values, and the bids/asks ordering as sent.
  - `min_order_size` is `"5"`, `neg_risk` is `false`, and `tick_size`/`last_trade_price` come from tracked state.
  - This matched the REST `/book` hash, the WS snapshot hash and a mid-stream WS `book` hash.
- **Replay test:** applying every `price_change` to the snapshot (set the level to `size`, delete it on `"0"`) reproduced **320 of 320** later `book` events exactly. Each `book.hash` equalled the last `price_change` hash for that asset.
- **Recorder rule:** compare against each `book` checkpoint (about 100 ms apart). On a mismatch, mark the gap and resync with REST `/book` or a resubscribe.
- **Rust SDK caveat:** `OrderBookSummaryResponse::hash()` uses SHA-256 of its own serialization, so it **will not match** the server's 40-hex SHA-1. Don't use it. [source-code: src/clob/types/response.rs:141]
- The Rust SDK models `PriceChangeBatchEntry.size`, `hash`, `best_bid` and `best_ask` as `Option`. [source-code]

## 2. REST (base `https://clob.polymarket.com`)

### `GET /book?token_id=<token>` [live-verified]

- **Live token** (HTTP 200):
  ```json
  {"market":"0xe315…","asset_id":"7603…","timestamp":"1793031404707","hash":"81a3b5ea8ac9c93c9717309745ae30992c7b7d85","bids":[{"price":"0.01","size":"10027.45"},…,{"price":"0.18","size":"1625.48"}],"asks":[…,{"price":"0.19","size":"13"}],"min_order_size":"5","tick_size":"0.01","neg_risk":false,"last_trade_price":"0.810"}
  ```
  Sorting is the same as on WS: best bid and best ask are last.
- **Resolved token:** `HTTP 404 {"error":"No orderbook exists for the requested token id"}`.

### `GET /clob-markets/{condition_id}` [live-verified]

- **Live market:**
  ```json
  {"r":{"mi":50,"ma":4.5,"moas":30},"t":[{"t":"7603…","o":"Up"},{"t":"7496…","o":"Down"}],"c":"0xe315…","mos":5,"mts":0.01,"mbf":1000,"tbf":1000,"ao":true,"aot":"2026-10-25T16:22:36Z","itode":true,"fd":{"r":0.07,"e":1,"to":true},"v":"v1"}
  ```
- **Resolved market:** same shape, but **`ao` is omitted**: `{"r":…,"t":…,"c":"0xa086…","mos":5,"mts":0.001,"mbf":1000,"tbf":1000,"aot":"2026-10-25T16:08:00Z","itode":true,"fd":{"r":0.07,"e":1,"to":true},"v":"v1"}`.
- **What each field tells you:**
  - There is **no `closed`, `winner` or resolution field.** [live-verified, docs]
  - `ao` = accepting orders. It is present (`true`) while trading and was still `true` 103 s after the window end, before resolution. It is absent after resolution. [live-verified]
  - `mts` is the current tick and switches to 0.001 near the extremes. [live-verified]
- **SDK coverage:** the SDK maps `c, t, mts, mos, nr, fd, mbf, tbf, rfqe` and ignores `ao, aot, itode, v`, so you need your own struct to read those. [source-code]
- **Docs mismatch:** the docs schema lists `gst, rfqe, ibce, oas` and says `itode` means a 250 ms hold. The changelog says the delay has been 150 ms since 2026-09-04. [docs]

### `GET /markets/{condition_id}` [live-verified] — this is the resolution and winner source

- **Resolved market:**
  ```json
  {"enable_order_book":false,"active":true,"closed":true,"archived":false,"accepting_orders":false,"accepting_order_timestamp":"2026-10-25T16:08:00Z","minimum_order_size":5,"minimum_tick_size":0.001,"condition_id":"0xa086…","question_id":"0xda00…","market_slug":"btc-updown-5m-1793030400","end_date_iso":"2026-10-26T00:00:00Z","seconds_delay":0,"maker_base_fee":1000,"taker_base_fee":1000,"neg_risk":false,"is_50_50_outcome":false,"tokens":[{"token_id":"2700…","outcome":"Up","price":0,"winner":false},{"token_id":"7142…","outcome":"Down","price":1,"winner":true}],"version":"v1"}
  ```
- **Ended but unresolved** (103 s after the end): `"enable_order_book":true,"closed":false,"accepting_orders":true`, and both tokens have `"winner":false` with prices 0.0005 and 0.9995.
- **Resolution rule:**
  - Resolved means `closed == true` **and** exactly one `tokens[].winner == true`.
  - At the same moment `accepting_orders` and `enable_order_book` go false, `/book` returns 404, and `/clob-markets` drops `ao`.
- **Pitfalls:**
  - `end_date_iso` holds only the date, so it is useless for timing.
  - `tokens[].price` is not live (it showed 0.305 while the book was 0.18/0.19).
- **Cross-check:** Gamma `events/slug/<slug>` agreed for the old window: `closed:true`, `umaResolutionStatus:"resolved"`, `outcomePrices:["0","1"]`, `closedTime:"2026-10-26 16:06:20+00"`.
- **Not measured:** the exact time of the transition (my poller's first sample came too late to catch it).

### Rate limits [docs: api-reference/rate-limits]

- Limits are per IP and enforced by Cloudflare on sliding windows. Requests over the limit are **delayed or queued, not rejected**; the page doesn't mention 429.
- CLOB public endpoints:

| Endpoint | Limit |
|---|---|
| General | 9,000 req / 10 s |
| `/book` | 1,500 req / 10 s |
| `/books` | 500 req / 10 s |
| `/price`, `/midpoint` | 1,500 req / 10 s |
| market tick size | 200 req / 10 s |

- `/markets/{id}` and `/clob-markets/{id}` have no limit of their own listed, so assume the general 9,000/10 s.
- Gamma: `/events` 500 req / 10 s, `/markets` 300 req / 10 s.
- No WebSocket limits are published.
- No rate-limit headers appeared on `/book` or `/clob-markets` responses. [live-verified]

# Topic: polybolt

# PolyBolt + Chainlink TWAP: wire-level report for the M1 recorder (checked 2026-10-26)

**Headline:**
- PolyBolt needs CLOB API credentials. The handshake sends the three values in plain text in the first frame; there is no HMAC.
- The legacy RTDS feed is still live with no authentication. Its 60 s TWAP value at the window-end timestamp **exactly equalled** Gamma `finalPrice` for BTC, ETH and SOL in one window I tested.
- There is no UI for CLOB L2 keys. You derive them from the signer key.

Tags: [live-verified] = I saw it on the live endpoint today. [source-code] = official SDK source on GitHub. [docs] = docs.polymarket.com or the AsyncAPI contract. [unverified] = not confirmed.

## 1. PolyBolt `wss://ws-live-v2.polymarket.com/ws`

**Contract and docs**
- Machine-readable contract: `https://ws-live-v2.polymarket.com/asyncapi.json` (AsyncAPI 3.0.0, version "2.0.0", public). [live-verified]
- Docs: https://docs.polymarket.com/api-reference/live-data/overview.md, https://docs.polymarket.com/api-reference/wss/polybolt.md, https://docs.polymarket.com/migrate/rtds-to-polybolt.md

**Timeline** [docs] (changelog at https://docs.polymarket.com/changelog/predictions.md; release dates from npm/PyPI)
- 2026-09-15: PolyBolt launched, and RTDS became legacy for prices.
- 2026-09-23: SDK 0.11.0 released. Removal of RTDS price topics was "planned one month after" this, so about 2026-10-23. It had not happened yet today (see section 2).
- 2026-09-29: `source` field added to payloads, plus `price.equity.twap`.
- 2026-10-02: `price.crypto` defaults to Chainlink; `provider` pin added.
- 2026-10-21: equity `market_status` added.

**Authentication** [docs + asyncapi; error shapes live-verified]
- It is a JSON text frame sent on the open socket. There are no headers and no HMAC: the raw L2 trio goes in plain text.
  ```json
  {"op":"auth","rid":"a1","auth":{"apiKey":"<key>","secret":"<base64 secret>","passphrase":"<pass>"}}
  ```
- Success reply: `{"op":"authed","rid":"a1"}`.
- The `auth` object holds either the CLOB trio or `{"accessToken":"<IdP JWT>"}` (RS256), never both. The web app uses `{"op":"auth","ticket":"..."}` instead (a Turnstile ticket from `POST /api/ws-ticket`). That route is not for us.
- Error replies seen live (the connection stays open):
  - Dummy values: `{"op":"error","rid":"a1","code":"auth_invalid"}`
  - Incomplete trio: `{"op":"error","rid":"a2","code":"bad_op"}`
  - Gated subscribe before auth: `{"op":"error","channel":"price.crypto.twap","rid":"s1","code":"auth_required"}`. This fires before any check of `window_seconds`.
- Other codes [asyncapi]: `auth_unavailable` (retry later), `auth_attempts` (9th auth frame, then close 4008), `bad_channel`, `bad_filter`, `sub_limit`, `rate_limited`, `auth_expired`.

**Subscribe** [docs/asyncapi]
- Batch form (one frame counts once against the rate limit):
  ```json
  {"op":"subscribe","rid":"s1","subscriptions":[
    {"channel":"price.crypto","filter":{"symbol":"btcusd"}},
    {"channel":"price.crypto","filter":{"symbol":"ethusd"}},
    {"channel":"price.crypto","filter":{"symbol":"solusd"}},
    {"channel":"price.crypto.twap","filter":{"symbol":"btcusd","window_seconds":60}},
    {"channel":"price.crypto.twap","filter":{"symbol":"ethusd","window_seconds":60}},
    {"channel":"price.crypto.twap","filter":{"symbol":"solusd","window_seconds":60}}]}
  ```
- Singular form: `{"op":"subscribe","channel":"...","filter":{...},"rid":"..."}`.
- Symbols must be lowercase `xxxusd`. The TWAP channel has data only for `window_seconds: 60`.
- Optional on `price.crypto`: `"provider":"chainlink"|"pyth"`. Omitting it gives Chainlink, and the `subscribed` ack names the provider actually served. `price.crypto.twap` is Chainlink only.
- Unsubscribe uses the same shape with `op:"unsubscribe"`; the server replies with `unsubscribed`.

**Replies and snapshots** [docs/asyncapi]
- Ack: `{"op":"subscribed","channel":"price.crypto.twap","rid":"s1"}` (may also carry `"provider"`).
- Each **new** subscription then gets exactly one snapshot frame (`"snapshot":true`). Its `data` array holds the previous 2 minutes of points, or is empty.
- A duplicate subscribe gets another ack but no new snapshot.

**Envelope and schema** [asyncapi]. Sample payloads below are from the docs; I could not capture these channels live without credentials.
- Live `price.crypto` frame:
  ```json
  {"v":1,"channel":"price.crypto","seq":2,"ts":1788973001000,
   "payload":{"symbol":"btcusd","value":64126.0,"full_accuracy_value":"64126.00000000","timestamp":1788973001000,"source":"chainlink"}}
  ```
- Live `price.crypto.twap` frame (TwapPoint). Required fields: `symbol` (str), `value` (number), `full_accuracy_value` (str), `timestamp` (int ms), `window_seconds` (int, const 60), `source` (const "chainlink"):
  ```json
  {"v":1,"channel":"price.crypto.twap","seq":N,"ts":<ms>,
   "payload":{"symbol":"btcusd","value":<f64>,"full_accuracy_value":"<decimal str>","timestamp":<ms>,"window_seconds":60,"source":"chainlink"}}
  ```
- Snapshot frame:
  ```json
  {"v":1,"channel":"price.crypto.twap","seq":1,"ts":<ms>,"snapshot":true,
   "payload":{"symbol":"btcusd","window_seconds":60,"source":"chainlink",
              "data":[{"timestamp":<ms>,"value":<f64>,"full_accuracy_value":"<str>"}]}}
  ```
  The points in `data` carry no `symbol` and no `source`. A `price.crypto` snapshot has the same shape without `window_seconds`.
- Field rules:
  - `seq` is dense per connection and per channel. Snapshots use up a seq number. It resets on reconnect.
  - `dropped` (int) appears only when frames were dropped for a slow consumer; it is absent when zero.
  - `ts` is the producer's event time in ms.
  - Prefer `full_accuracy_value`. It is a decimal string and is **not** E18; the E18 format was RTDS only.
  - `source` can change between connections, so re-read it after every reconnect.
  - Don't drop an update just because its timestamp repeats.

**Heartbeat** [docs]
- The server sends a WebSocket protocol ping every 25 s; standard clients answer automatically. Two missed pongs close the connection with code 4002.
- An optional application-level ping is also available: `{"op":"ping","rid":"p1"}` gets `{"op":"pong","rid":"p1"}`. [live-verified]
- Do not send a text `PING`.

**Limits and close codes** [docs/asyncapi]

Limits per connection:

| Limit | Value | On breach |
|---|---|---|
| Active (channel, filter) pairs | 64 | `sub_limit`, then close 4008 |
| Subscribe/unsubscribe frames | 20 per second | `rate_limited`, then close 4008 |
| Frame size | 64 KB | close 4008 |
| Auth frames | 8 | `auth_attempts`, then close 4008 |

A socket that neither authenticates nor subscribes within 120 s may be closed with 4008 and reason `unengaged` ("once enforced").

| Close code | Meaning | What to do |
|---|---|---|
| 4001 | Auth failed | Fix credentials before reconnecting |
| 4002 | Slow consumer or pong timeout | Exponential backoff with jitter |
| 4003 | Server draining | Reconnect once after a uniform random 0–10 s |
| 4008 | Policy violation | Treat as a bug; don't reconnect blindly |
| 1008 | Access token expired | Not relevant with CLOB credentials |
| 1006 | Abnormal close | Full-jitter backoff, 1 s up to a 30 s cap |
| HTTP 429/503 on handshake | Rate limited or unavailable | Honour `Retry-After`, add jitter |

After a reconnect: authenticate again, resend all subscriptions (including provider pins), reseed from the new snapshots, and re-read `source`.

**Bonus: a public channel that needs no auth** [live-verified]
- `{"op":"subscribe","rid":"s1","channel":"price.polymarket","filter":{"asset_id":"<clobTokenId>"}}` returns `subscribed`, then a snapshot, then a frame on every book-hash change (several per second):
  ```json
  {"v":1,"channel":"price.polymarket","seq":2,"ts":1793031260696,"payload":{"asset_id":"2280…4330","best_ask":"0.01","best_bid":"0","hash":"7ffd9ee4…","market":"0x6fc2…1eb7","timestamp":1793031260696}}
  ```
- `{"op":"challenge"}` returns `{"op":"challenge","nonce":"<uuid>","rid":"c1"}`. This is for the web app only.

**SDK support for PolyBolt**
- `@polymarket/client` ≥0.11.0: `createSecureClient(...)` then `client.subscribe([{topic:"prices.crypto.twap",symbols:["btcusd"]}])`. [docs]
- `polymarket-client` (Python) ≥0.11.0: `AsyncSecureClient.subscribe(CryptoTwapPriceSpec(symbols=["btcusd"]))`. [docs] Latest version of both is 0.14.0, released 2026-10-21.
- `rs-clob-client-v2` (crate `polymarket_client_sdk_v2` 0.8.0) has **no PolyBolt support**. [source-code]
  - Its `rtds` feature (`src/rtds/client.rs`) only targets `wss://ws-live-data.polymarket.com` and the legacy topics `crypto_prices` and `crypto_prices_chainlink`. It has no TWAP helper; `subscribe_raw` exists.
  - We hand-roll the PolyBolt client, as CLAUDE.md already expects.

## 2. Legacy RTDS `wss://ws-live-data.polymarket.com`: still live with no auth today [live-verified]

**Subscribe**
- `filters` is a **JSON-encoded string**:
  ```json
  {"action":"subscribe","subscriptions":[
    {"topic":"crypto_prices_twap_sixty","type":"*","filters":"{\"symbol\":\"btc/usd\"}"},
    {"topic":"crypto_prices_chainlink","type":"*","filters":"{\"symbol\":\"eth/usd\"}"},
    {"topic":"crypto_prices","type":"update"}]}
  ```
- `"filters":""` on a topic gives all 8 symbols (btc, eth, sol, xrp, doge, hype, bnb, zec).

## 3. Getting CLOB L2 API credentials (apiKey / secret / passphrase)

**Is there a settings page for them?** No. polymarket.com → Settings → API Keys offers only **Relayer API Keys** (gasless operations, needed for redeem) and **Builders** (builder key, secret and passphrase). Neither is the CLOB L2 trio. [docs: trading/wallets-auth.md]

**How they are created** [docs: getting-started/api.md]
- They come from an EIP-712 L1 signature by the signer's private key.
- Typed data: domain `{"name":"ClobAuthDomain","version":"1","chainId":137}`, primaryType `ClobAuth`, fields `{address, timestamp (string, unix s), nonce (uint256, use 0), message:"This message attests that I control the given wallet"}`.
- Create: `POST https://clob.polymarket.com/auth/api-key`. Derive (idempotent): `GET https://clob.polymarket.com/auth/derive-api-key`.
- Both take headers `POLY_ADDRESS`, `POLY_SIGNATURE`, `POLY_TIMESTAMP`, `POLY_NONCE`.
- Response: `{"apiKey","secret","passphrase"}`. The secret is base64 and is used for HMAC-SHA256 on REST calls only, not for PolyBolt.

**Rust** [source-code: `src/clob/client.rs`]
- `Client::new(host, Config)?.create_or_derive_api_key(&signer, None).await -> Result<Credentials>`. Also available: `create_api_key` and `derive_api_key`.
- Or: `.authentication_builder(&signer).signature_type(SignatureType::Poly1271).funder(deposit_wallet_addr).authenticate().await`. This calls `create_or_derive_api_key` internally, and `client.credentials()` returns the trio.
- The signer must have its chain ID set: `LocalSigner::from_str(pk)?.with_chain_id(Some(POLYGON))`.
- The example uses host `https://clob-v2.polymarket.com`; the docs use `clob.polymarket.com`.

**Python** [source-code: py-clob-client-v2 README]
```python
from py_clob_client_v2 import ClobClient
creds = ClobClient(host=host, chain_id=137, key=os.environ["PK"]).create_or_derive_api_key()
```
The new SDK (`polymarket-client`) does the same inside `AsyncSecureClient.create(private_key=..., wallet=...)`.

**Deposit Wallet accounts (signature type 3, `POLY_1271`)** [source-code / docs]
- Credentials belong to the **signer EOA** (`POLY_ADDRESS` = the account or session signer), not to the deposit wallet.
- For orders, `funder`/maker = the Deposit Wallet address, and the Rust SDK refuses `Poly1271` without a funder.
- So the user needs the account's owner signer private key. Alternatively, the owner can authorize a **Session Key**: a separate EOA, authorized through a Relayer transaction that needs a Builder API key (docs: trading/session-keys.md). The session EOA then derives its own CLOB credentials.
- How a polymarket.com email/Google user exports the owner key: the docs don't say. [unverified]
- PolyBolt read-only auth probably works with credentials derived from **any** EOA, even an unfunded one with no deposit wallet. L1 auth only proves you control the key, and PolyBolt just checks the trio. I did not test this because it means minting credentials. [unverified] It would be the quickest way to start M1 PolyBolt recording without touching the trading account's key, but check the terms first.

## Two findings that change the M1 design

- **Gamma responses are cached by CloudFront for up to 300 s** [live-verified]. Every response carries `cache-control: public, max-age=300` and `x-cache: Hit from cloudfront`, with `age` values of 141–230 s seen. The `date` header is when the origin built the response, not now.
  - `/events/slug/`, `/events?slug=`, `/markets?slug=` and `/markets/slug/` are all cached this way.
  - Adding a unique query parameter (`?cb=<unix>`) gave `x-cache: Miss from cloudfront` and fresh data. Whether we use that or accept data up to 5 minutes old is a policy decision.
  - Treat Gamma as up to 5 minutes stale unless you bust the cache.
- **`priceToBeat` and `finalPrice` arrive in Gamma minutes late** [live-verified]. In the cache-busted samples, `eventMetadata` showed up 4 to 6 minutes after the matching window boundary and well after on-chain resolution. Gamma cannot supply the live price to beat; M1 must record the TWAP itself, as CLAUDE.md §2 already plans.

## 3. tokio-tungstenite: WebSocket client API
**Connecting** [source-code]
- `connect_async(url) -> Result<(WebSocketStream<MaybeTlsStream<TcpStream>>, Response)>`
- `connect_async_with_config(req, Option<WebSocketConfig>, disable_nagle: bool)`
- `connect_async_tls_with_config(req, cfg, disable_nagle, Option<Connector>)`

**WebSocketConfig defaults** [source-code]
- `read_buffer_size` 128 KiB, `write_buffer_size` 128 KiB, `max_write_buffer_size` unlimited.
- `max_message_size` 64 MiB, `max_frame_size` 16 MiB.

**Ping frames are answered automatically while you read** [source-code]
- When `read()` gets a Ping frame, it queues a Pong (`set_additional(Frame::pong(data))`).
- At the top of every `read()` loop it flushes queued replies ("we need to reply to the messages even during read").
- `Stream::poll_next` calls `read()`, so simply driving `ws.next().await` sends Pongs.
- Don't reply to Ping manually. Ping frames are still yielded to you as `Message::Ping` (record or ignore).
- One caveat after `split()`: the auto-Pong is written through the shared inner socket on the next `read()`. That works because SplitStream and SplitSink share a BiLock. [unverified: I didn't check the BiLock implementation]

**Sending the application-level text PING** [source-code]
- `ws.send(Message::Text("PING".into())).await?` (via `SinkExt`).
- The reply arrives as `Message::Text(t)` with `t == "PONG"`. This is exactly what the SDK does in `ws/connection.rs`.

**Raw text**
- `Message::Text(Utf8Bytes)`: `t.as_str()` gives the exact server bytes.
- Write those to the recorder **before** parsing.

## 4. Raw-preserving JSON and decimals
- **RawValue.** With serde_json `raw_value`, you can use `Box<serde_json::value::RawValue>`, or borrowed `&'a RawValue` with `#[serde(borrow)]`, for untouched sub-objects. [docs]
- **Decimal default deserialize** uses `deserialize_any`. A JSON *string* goes to `from_str` (exact). A JSON *number* goes through f64, then `to_string()`, then `from_str`, which is shortest-round-trip and **loses digits beyond about 15–17 significant figures**. [source-code: `serde.rs:343-347`]
- **Polymarket and Binance prices are strings**, so use `#[serde(with = "rust_decimal::serde::str")]` (feature `serde-with-str`). [source-code]
- **For JSON-number prices** (Coinbase/PolyBolt numeric fields, if any), either:
  - enable `serde-with-arbitrary-precision`, which **switches serde_json `arbitrary_precision` on for the whole workspace** and changes how `serde_json::Value` handles numbers (known friction with `flatten`/`untagged` — [unverified]); or
  - keep the raw text and parse those fields with `RawValue` → `Decimal::from_str(raw.get())`.
  - I recommend the second option.
- Decimal serializes as a JSON string by default. [docs]

## 5. zstd streaming (crash safety)
**Live test** with libzstd 1.5.7 and the `zstd` 1.5.7 CLI. Script: `/private/tmp/claude-502/-Users-Radivoje-Dundjerovic-Private-Projects-raki-trader/329f98a4-f0bc-40e8-8200-4d37b870c3fe/scratchpad/zt_test.py`. [live-verified]
- 1000 JSON lines were compressed with checksum on, flushing (`ZSTD_e_flush`) every 100 lines. The process "crashed" after line 600 without ending the frame.
- **All 600 flushed lines decoded.** `zstd -dc` printed all 600, then exited with rc=1 and "Read error"/truncated. The Python decoder returned 600 lines with `eof=False`.
- Tearing the file 7 bytes into the last flushed block gave **500 lines**. Everything up to the previous flush survived, and the torn block was lost whole, with no garbage.

**Rust zstd 0.14.3 API** [source-code]
- `zstd::stream::write::Encoder::new(w, level)`.
- `Write::flush()` calls `ZSTD_e_flush` (`zio/writer.rs:286`). This ends the current block so everything written so far can be decoded. Then it flushes the inner writer.
  - It does **not** fsync. Call `file.sync_data()` separately if you need durability against an OS crash, not just a process crash.
- To end a frame: `finish() -> io::Result<W>`, `try_finish()`, `do_finish(&mut self)`, or `auto_finish()` (finishes on drop).
- Options (`encoder_common!`): `include_checksum`, `multithread` (with `zstdmt`), `window_log`, `long_distance_matching`, `set_pledged_src_size`.
- Multiple frames concatenated in one file are decoded by default. `Decoder::single_frame()` turns that off.

**Reading a truncated file** [source-code]
- `zstd::stream::read::Decoder` (or `Decoder::new(File)` wrapped in a `BufReader`) returns the decodable bytes, then **`io::ErrorKind::UnexpectedEof` with the message "incomplete frame"** (`raw.rs:269-274`).
- The reader should:
  - treat that error at EOF as a "truncated tail" marker;
  - drop any final line without a trailing `\n`;
  - log how many bytes were recovered.

**Recommended writer pattern**
- One frame per hourly file.
- Flush at record boundaries every N ms or N records.
- `finish()` and `sync_all()` at rotation.
- On startup, if a file was not finished, open a new file rather than appending to the torn one. [inference from the tests above]

## 8. macOS sleep/wake detection
- On Apple targets, std `Instant` uses **`CLOCK_UPTIME_RAW`**: "does not increment while the system is asleep … identical to mach_absolute_time()". The std source says so (`library/std/src/sys/time/unix.rs:55-67`), and so does `man clock_gettime` on macOS 26.5. [source-code + live-verified]
- On macOS, `CLOCK_MONOTONIC` "will continue to increment while the system is asleep". [live-verified, man page]
- `tokio::time` is built on std `Instant`, so tokio timers and intervals effectively stop during sleep. [inference]
- **Detector:** every 1 s, compute `drift = Δ(libc::clock_gettime(CLOCK_MONOTONIC)) − Δ(Instant)`.
  - This is immune to NTP steps. Comparing SystemTime against Instant also works, but an NTP step can trigger it falsely.
  - If drift > 2 s, emit a `system_sleep{slept_ms}` gap event and force-reconnect every feed.
- **This Mac does sleep:** `pmset -g log` shows **359 "Entering Sleep" entries**. Run the recorder under `caffeinate -is <cmd>` and check `pmset -g assertions`. [live-verified]

  ```json
  {"stream":"btcusdt@trade","data":{"e":"trade","E":1793042329366,"s":"BTCUSDT","t":6793695684,"p":"80090.73000000","q":"0.00022000","T":1793042329366,"m":true,"M":true}}
  ```
- **Pings and connection lifetime** [docs]: the server sends a WebSocket ping every 20 s; tungstenite answers it automatically. Connections are cut after 24 h, so reconnect.
- **Prices** are strings in USDT. Convert to USD with Coinbase `USDT-USD`.

## Coinbase Exchange feed [live-verified]

- **URL:** `wss://ws-feed.exchange.coinbase.com`. No auth for `ticker` and `heartbeat`.
- **Subscribe** (must be sent within 5 s of connecting [docs]):
  ```json
  {"type":"subscribe","product_ids":["BTC-USD","ETH-USD","SOL-USD","USDT-USD"],"channels":["ticker","heartbeat"]}
  ```
- **Ack:**
  ```json
  {"type":"subscriptions","channels":[...]}
  ```
- **`ticker`** fires once per trade and includes the best bid/ask. `time` is an RFC 3339 string with µs precision:
  ```json
  {"type":"ticker","sequence":138368971014,"product_id":"BTC-USD","price":"79960.18","best_bid":"79959.29","best_bid_size":"0.14977792","best_ask":"79960.18","best_ask_size":"0.00088474","side":"buy","time":"2026-10-26T19:18:52.053821Z","trade_id":1110932933,"last_size":"0.00411777"}
  ```
- **`heartbeat`** is sent once per second per product. Use `last_trade_id` to spot gaps:
  ```json
  {"type":"heartbeat","last_trade_id":850440923,"product_id":"ETH-USD","sequence":104376383811,"time":"2026-10-26T19:18:53.000000Z"}
  ```
- **USDT-USD** traded about 0.9985, which is the USDT→USD conversion for Binance prices.
